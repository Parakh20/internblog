# Decision Log

One entry per nontrivial architecture or library choice, with rationale.

| Date | Decision | Rationale |
|------|----------|-----------|
| 2026-07-13 | Repo initialized before any code; incremental commits per logical change | Requested workflow: small checkpointed increments, easy rollback and review |
| 2026-07-13 | Monitor via WordPress REST API over plain HTTP, not Playwright | Blog is stock WordPress behind mod_auth_openidc; REST returns structured JSON with modified timestamps using only the session cookie. Lighter and more reliable than a browser. See investigation.md |
| 2026-07-13 | Playwright kept only for manual re-auth (scripts/reauth.py) | SSO login must stay manual per constraints; visible browser plus saved storage state is the simplest safe flow |
| 2026-07-13 | Silent session refresh added before pause-and-alert | Observed the blog session dies after roughly 8 idle minutes while the SSO session lives much longer. A headless browser visit completes the OIDC redirect with zero credential entry, same as the user's own browser. If SSO shows a login form the refresh backs off and alerts. Deviation from the original pause-immediately spec, flagged for review |
| 2026-07-13 | Session cookie rotation persisted from Set-Cookie headers | mod_auth_openidc rotates the session cookie; ignoring rotation strands the monitor on a stale value |
| 2026-07-13 | Claude model claude-opus-4-8 via messages.parse structured outputs | Guaranteed schema-valid extraction, no JSON repair code. Model configurable via ANTHROPIC_MODEL if cost becomes a concern |
| 2026-07-13 | Change detection requires both timestamp and content hash to differ | WordPress can bump modified_gmt without a real content change; hash guard avoids noise alerts |
| 2026-07-13 | SQLite for dev, Postgres via compose for deploy, same SQLAlchemy models | Single code path, switched by DATABASE_URL |
| 2026-07-13 | Extraction failures never block post storage | Posts are stored first; scripts/backfill_extractions.py re-runs extraction later (needed today: API credit balance was empty) |
| 2026-07-17 | Poll interval tightened to 2 min, refresh cooldown to 90s | Blog session can die within 1-2 idle minutes and, once dead, doesn't redirect straight back to the blog (requires manual portal clicks unless caught by silent refresh first). Frequent polling itself acts as the keep-alive |
| 2026-07-17 | Groq's own free tier is the primary extraction provider; OpenRouter's rotating `:free` model list is now a secondary fallback chain, tried via a list of (client, model) attempts | OpenRouter's free models are secondhand capacity that gets pulled/saturated with no notice (happened three times: Anthropic credits, Llama, then gpt-oss-120b). Groq's free tier is a published, stable rate limit from the actual provider |
| 2026-07-17 | Added `is_job_posting` column to Extraction, backfilled from existing raw_json | Needed to filter PPT/administrative posts out of notifications and the calendar feed without re-parsing JSON on every query |
| 2026-07-17 | Telegram bot for push notifications, ICS feed for Google Calendar (Codeforces-style) | Single-user tool: Telegram is free and instant. The ICS feed is pull-based (Google polls on its own schedule, not instant) so it complements rather than replaces Telegram |
| 2026-07-17 | Oracle Cloud Free Tier (Ampere A1, 4 OCPU/24GB RAM) chosen for deployment over GCP e2-micro and Azure | Only permanent free compute option with enough RAM headroom for Postgres + FastAPI + occasional headless Chromium; GCP's free tier is 1GB RAM (tight), Azure's is a 12-month trial only |
| 2026-07-17 | Reversed: deployed on Azure for Students instead of Oracle Cloud | User already had an Azure for Students credit ($100/12mo) and preferred to use it now rather than open a separate Oracle account. Oracle's Always Free tier remains the better long-term (permanent, free) option if the Azure credit runs out |
| 2026-07-17 | VM recreated as Arm64 (`Standard_B2pls_v2`) after the initial x64 `Standard_B2ats_v2` (1GB RAM) OOM'd and locked up under Postgres+FastAPI+Caddy+Chromium | Larger x64 burstable/general-purpose sizes were `NotAvailableForSubscription` or out of regional capacity for this student subscription in southeastasia; Arm64 burstable sizes (4GB+) were available. Azure can't resize x64→Arm64 in place, so the VM was deleted and recreated on the same NIC/public IP (DNS unaffected). All Docker images in use are multi-arch |
| 2026-07-17 | DuckDNS (free) used for the hostname Caddy needs for Let's Encrypt, domain registration deferred | User doesn't yet own a domain; DuckDNS is free and immediate. Can swap to a real domain later by just changing `CADDY_DOMAIN` |
| 2026-07-17 | Added richer `category` classification (new_listing/test_update/test_reschedule/ppt/shortlist_result/deadline_extension/administrative/other), replacing binary `is_job_posting` | User wants tests, reschedules, and PPTs routed to Telegram/calendar too, not just job postings, without repeating placement-office boilerplate in every message |
| 2026-07-17 | Direct push into the user's personal Google Calendar via the Calendar API, alongside the existing ICS feed | The official Google Calendar mobile app does not surface URL-subscribed "Other calendars" the way desktop does, so the ICS feed alone never reached mobile. OAuth client lives in a dedicated Cloud project (`internblog-cal-sp05`) owned by the user's personal Google account, not the axalon account |
| 2026-07-17 | Default extraction model switched from `llama-3.3-70b-versatile` to `llama-3.1-8b-instant` | The 70b model's Groq free-tier token-per-minute budget got exhausted under bulk backfill testing across all 45 real posts; the 8b model has a separate, higher-throughput free-tier bucket and classified all 45 posts correctly with zero failures once schema bugs (null-vs-empty-list, list-vs-string fields) were fixed |
| 2026-07-17 | Notify/calendar-push gated on the deadline actually being in the future (`_is_upcoming` in pipeline.py); post link dropped from Telegram messages | Backfilling extraction for 11 never-processed old posts fired real Telegram notifications and calendar events for already-elapsed mock test dates, since the original notify/push logic only checked category, not date. User also asked to stop repeating the raw blog link in every message |
| 2026-07-17 | Calendar event id keyed by `(company, event type)` via `event_id_for_company`, not by extraction row | User wants a deadline_extension (or test_reschedule) to modify the company's existing calendar event in place, not create a duplicate. Event type is grouped (new_listing+deadline_extension share "deadline"; test_update+test_reschedule share "test") so genuinely different occasions for the same company - e.g. a PPT vs. the application deadline - still stay separate events |
| 2026-07-17 | Same grouping applied to Telegram via a new `telegram_notifications` table (group_key -> message_id) and `editMessageText`, falling back to a new send if the edit fails | Consistent with the calendar behavior: a deadline_extension should edit the original notification in place rather than sending a duplicate message |
| 2026-07-17 | Dashboard (`/`) expanded with an "Upcoming calendar events" section and a full "Database" table (all extractions, not just last 15) | User checks this URL directly for health/analysis and wants to see calendar contents and the underlying extraction data without needing DB access |
| 2026-07-17 | Google Calendar push moved from the user's primary personal calendar to a dedicated "Internblog Deadlines" secondary calendar | Pushing into `primary` mixed internship events with the user's actual personal calendar (lectures, gym, etc.) - a real usability problem, not just a display issue. Required broadening the OAuth scope from `calendar.events` to `calendar` (needed to create a calendar), redoing the one-time consent |
| 2026-07-17 | IST-parsing logic consolidated into one shared `app/timeutil.py` (`parse_ist`, `parse_gmt`), replacing three near-duplicate implementations | Was about to add a fourth (dashboard display) - a good point to deduplicate. `parse_gmt` added separately since WordPress's `date_gmt`/`modified_gmt` fields are naive-but-UTC, the opposite assumption from the blog-content IST convention `parse_ist` encodes |
| 2026-07-17 | Dashboard "Database" table sorts by `Post.date_gmt` (when the post appeared on the blog), not the extracted deadline or our own extraction timestamp | User's requirement, after two rounds of clarification: neither "when we extracted it" nor "the event's own deadline" was the intended sort key - it's specifically when the post was published |
| 2026-07-17 | Added `InternshipExtraction._normalize_dates`: clamps any extracted year below 2026 up to 2026, and combines a bare time-only value with the post's own `date_gmt` as a fallback date | Two real data-quality issues seen on live posts: PPT/test dates occasionally coming back a year early despite the prompt stating the season explicitly, and a deadline extracted as just "11:00:00" with no date at all (previously silently dropped by every downstream consumer, since all require a full ISO datetime) |
| 2026-07-18 | Site converted from single-user to public multi-user: Google OAuth login (Authlib) required for the whole site, server-side sessions in a new `sessions` table, per-user `users` table storing an encrypted Calendar refresh token and optional Telegram chat id | User wants to open the tool to other people, each syncing the same shared internship postings to their own calendar/Telegram rather than the original hardcoded single target |
| 2026-07-18 | Admin/status dashboard moved from `/` to `/admin`, gated to `sharmaparakh05@gmail.com` by email, returning 404 (not 403) for anyone else | Public visitors shouldn't see session/fetch-log internals; 404 avoids confirming the route exists to non-owners |
| 2026-07-18 | Google Calendar refresh tokens encrypted at rest with Fernet (`app/crypto.py`), keyed by a new `SECRET_ENCRYPTION_KEY` | Multi-user means many long-lived personal-calendar credentials now live in the DB instead of one value in `.env` - plaintext storage would be a real exposure if the DB leaked |
| 2026-07-18 | Full extraction database, last fetch time, poll interval, and total extraction count moved from admin-only `/admin` onto the public `/` page for every signed-in user | User's explicit request: this data (scraped blog postings) isn't sensitive, only the session/fetch-log operational internals should stay admin-only |
| 2026-07-18 | Manual Telegram chat-id entry replaced with a `/start` deep link (`t.me/<bot>?start=<code>`) plus a webhook at `/telegram/webhook`, correlated via a single-use `User.telegram_link_code` | Telegram's Bot API can't message a user by @username - it requires the user to message the bot first regardless. The deep link automates that first-contact message into a single tap instead of requiring a manual `getUpdates` JSON lookup |
